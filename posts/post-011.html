Relocation & Compensation System

房屋征收补偿协议与回迁安置选房系统

一套自研的全流程管理平台 · 覆盖住户建档、补偿测算、协议生成、财务支付、交房验收、回迁选房与结算

征收项目的日常，往往是一地鸡毛：住户信息散落在十几个 Excel 里，街道、社区、评估公司各存一份；补偿口径靠"老师傅"记，同一套房两个人能算出两个数；协议用 Word 手改，改错一个数字就要重新打印、重新签字；付款、交房、选房各自一本账，月底对不上；领导要进度，只能等别人汇总。

我把这套活儿收进了一个系统——从住户建档、补偿测算、协议生成打印，到财务支付、交房验收、回迁选房与结算，做成了一条完整的业务闭环。它最初为某市辖区的棚户区/片区改造项目开发并实际投用，后来经过重构支持多项目隔离，可以作为同类征收项目的通用底座。这篇文章，把它完整地讲一遍。

"同一个住户，在哪里看都是同一个数。"

一、它到底解决了什么

现实痛点系统的做法
数据分散在十几个 Excel一套住户档案，街道/社区/评估公司共用，按 project_id 隔离
口径不一，两人算两笔账补偿规则集中在配置项，全站只调一个计算入口 calculateCompensation()
协议用 Word 手改易错Word 模板 + 占位符，生成即填数，明细行按条件自动删减
付款/交房/选房对不上账协议 → 领款单 → 收款单 → 交房单 → 选房结算，全链路可追溯
进度不透明领导看板 / 签约示意图 / 立面图，按楼栋、院落实时呈现

二、系统全景：三大业务域

2.1 征收与补偿域

住户管理建档、共有人、分户、批量导入导出
签约示意图楼栋立面/院落布局，点击直接办业务
院落布局画板上传航拍底图，拖动摆放每户
补偿测算四类口径，独院走土地认定
协议生成选模板/期数/方式，一键生成 docx
协议预览与下载同源渲染，所见即所印
财务管理分两期开领款单、收款单、补缴通知
交房管理验收单、交房奖励、交房示意图
领导看板全/单项目总览，云端零 PII 镜像

2.2 回迁选房域（可按项目开关）

房源管理小区/楼栋/户型批量导入，面积单价维护
选房人核验扫码/查号核验身份，叫号排队
选房台现场选房、锁定房源，防一房两家
结算单超面积分档计价、不足回购、地下室、维修基金
确认书/合同模板化生成，可直接打印
差价收付收款单、链式追加，原单冻结
物业入住核对收款与选房后办理入住
选房模拟器住户自助试算，免登录、零储存

除此之外还有一组通用能力：多项目隔离（所有业务表带 project_id，配置分「全局 / 项目」两层，项目配置永久覆盖全局）；十类角色（管理员、打印员、财务、交房、住户管理、选房员、核验叫号、选房财务、选房打印、物业）；敏感字段加密落库；关键动作操作留痕可导出；零外部依赖——不引 CDN、不引前端框架、不引字体服务，内网/离线可用；二维码纯 PHP 生成。

三、补偿计算引擎：全站只调一个入口

整套系统最硬核的地方，是一条铁律——计算入口只有一个 calculateCompensation(array $data): array。协议预览、协议下载、列表、导出、财务、看板、公开试算全部调用它，不允许任何页面自己再算一遍。这是保证"同一个住户在哪里看都是同一个数"的前提。

3.1 房屋类型决定口径

类型中文计算口径10㎡ 安置奖励
building单元楼楼房有
townhouse联排式住宅楼楼房有
single独院院落（土地认定）无
big_yard / small_yard大/小伙院院落（土地认定）无

判定函数只有一处 isBuildingLikeType()，新增类型只需改这一处。即便把独院配置成"参照单元楼"，也只改单价与费用口径，不赠送 10㎡。

3.2 认定补偿面积

楼房类
认定补偿面积 = 建筑面积 + 10㎡（安置奖励面积）

10㎡ 只给楼房类；分户时按面积占比分摊，不是每人各加 10㎡。

院落类（土地认定）
认定补偿面积 = max(合法建筑面积, 合法土地面积 × 土地倍数)
临时建筑面积 = max(0, 合法建筑面积 − 合法土地面积 × 2)
计费基数 = min(合法建筑面积, 合法土地面积 × 2)

土地倍数默认 1.5、双倍系数默认 2，均为配置项；计费基数只影响过渡费，不影响房屋补偿。

3.3 奖励项：两种方案，按项目二选一

配置键 bonus_mode 存于 project_config，每个项目独立设置。

方案公式（示例值）说明
A · 户奖励第一期 80,000 / 第二期 40,000 / 第三期 0按期数（协议字段 sign_stage）判定，第三期整行消失
B · 面积奖励min(建面, 200㎡) × 400 元/㎡该方案下不计户奖励
经验：口径类改动最容易犯的错是"总额变了但没人发现"。每次改完 includes/compensation.php 后，必须跑内置自测（16 个用例）、与主系统交叉比对容差 0.01、抽查真实协议重印——差额必须为 0（除非本次就是要改钱）。

3.4 合计与分期

合计构成
合计 = 房屋补偿 + 面积奖励 + 户奖励 + 储藏室 + 搬迁费 + 回迁费 + 过渡费 + 临时建筑 + 营业补助 + 交房奖 + 附属物 − 补缴建安 − 模拟房改费
第二期 = min(交房奖, 合计)　|　第一期 = 合计 − 第二期

合计为负 → 视为补缴户，两期归零，走补缴通知单；第二期不能超过合计，避免扣减项把第一期压成负数。

四、回迁选房：防一房两家

选房结算与补偿协议分开：协议里算的是"应得补偿"，选房时算的是"多退少补"。住宅超面积分档计价（示例：≤20㎡ 按成本价 7000、>20㎡ 按市场价 10000），面积不足按回购单价（示例 8000）折现；地下室、维修基金另计。

现场最怕两个人同时抢一套房。xz_pick_item.house_id 建唯一索引，配合事务行锁——两个人同时选同一套房，只有一个能成功，另一个会提示"该房源已被选"。

五、技术架构：零框架、零构建

项版本 / 说明
PHP7.4+（生产验证于 8.2），需 openssl / zip / gd / pdo_mysql
数据库MySQL 5.6+ / MariaDB 10.x，utf8mb4
Web 服务器Nginx / Apache（附 deny 规则与 web.config）
前端原生 HTML + CSS + JS，无构建步骤
文档生成PHP ZipArchive 直接改写 docx 的 word/document.xml
依赖无 Composer、无 npm

代码刻意保持"零框架、零构建"，目的是让区县一级的运维人员能直接拷文件部署、出问题能看懂。五步即可上线：放目录 → 配数据库 → 建库 → 浏览器执行安装 → 删掉 install.php。

六、安全与隐私：把 PII 当回事

系统处理身份证号、手机号、银行卡号等敏感个人信息，属于《个人信息保护法》意义上的敏感场景。代码层面已落实的防护：

风险处理方式
SQL 注入全站 PDO 预处理，禁止拼接；动态列名走白名单
XSS输出统一 htmlspecialchars()；富文本白名单过滤
CSRF全站表单校验 token；删除类操作只接受 POST 并二次确认口令
越权角色 + 项目双维度校验；显示权限与出口权限分离
敏感字段身份证/手机号/银行卡 AES 加密存储；列表默认脱敏
口令存储password_hash()（bcrypt），不可逆
会话登录后重建 session id；闲置超时退出
日志关键操作留痕，保留期不少于 180 天（等保要求）
部署方必须完成的加固：修改数据库口令（别用 root）、改并删除 install.php、首登即改密、全站 HTTPS、includes/ 与 uploads/ 禁 Web 访问、上线后执行加密迁移、定期备份数据库与密钥文件（两者缺一不可）。开源仓库只保证代码层防护，上述事项由部署方负责。
